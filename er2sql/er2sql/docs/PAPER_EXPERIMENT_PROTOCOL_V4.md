# ER2SQL paper protocol v4 — reference policy amendment

Locked 7 October 2026, before any final-model outputs. This amendment
supersedes protocol v3 only for future runs. Historical manifests, pilots,
reports, source SQL, and split-selection evidence remain immutable. New paid
runs require freshly resolved manifests pinned to `config/paper_protocol_v4.yaml`.
No LLM calls are needed or authorized by this amendment.

## Authoritative schema and denominator

The authoritative schema is the relational end state of the original scraped
source DDL after every source `ALTER TABLE` operation is applied in source
order. It is not inferred from ER diagrams (Tier 2/3 intentionally hide
information), model output, or PostgreSQL-specific convenience additions.
Original SQL remains immutable. The deterministic planned test suite is built
once from this resolved gold state and reused identically for Structured,
Direct, and every model for a schema-tier cell.

## Approved conversion policy

The categories in `config/paper_protocol_v4.yaml` are approved at policy level.
No per-file semantic signature is required for a candidate whose changes are
only in those categories, which has no blockers, and which compiles and passes
all generated reference checks against PostgreSQL. The audit must record
`policy-approved: <category>; protocol v4 decision log` alongside source and
candidate hashes. This records the prospective category ruling; it must not be
misrepresented as an individual file review.

Approved categories include integer display-width removal; explicit
MySQL/Oracle type mappings (including bare/wildcard `NUMBER` to unconstrained
`NUMERIC`); `GENERATED BY DEFAULT AS IDENTITY`; comment metadata conversion;
index translation; removal of physical engine/encoding/collation options;
relocation of unchanged FKs; required reserved-word quoting; lowercase folding
of quoted identifiers unless a same-schema collision requires quoting; unsigned
integer widening without a synthetic check; `ENUM` membership checks with the
exact declared values; binary types to `BYTEA` without length/padding semantics;
removal of `ON UPDATE CURRENT_TIMESTAMP`; and `DOUBLE PRECISION` mapping.

## Exclusions and unresolved source cases

Exclude and document, before paid scoring, schemas with a source FK targeting a
non-unique column, conflicting duplicate table definitions with no resolvable
final version, an unrepresentable `SET` domain, unresolved or malformed source
DDL after the converter fixes, or any candidate that fails PostgreSQL execution
or generated reference tests. Exclude `schema_0924_372982` because its source is
SQLite's internal `sqlite_stat1` metadata, not an application schema. Never add
a key, type, or constraint merely to force compilation. `MATCH`,
`NULLS NOT DISTINCT`, and `EXCLUDE` are checked empirically in PostgreSQL; a
passing candidate is retained, a failing one is excluded and documented.

The converter must resolve `ALTER TABLE ADD/DROP` against accumulated source
state in order and strip `#` inline comments before parsing. Remaining
unresolvable operations are individually documented and excluded rather than
guessed. Any one-off semantic judgment not covered by this policy requires a
named reviewer, source/candidate hashes, and a concise semantic note.

## Reporting and run implications

The 20-schema pilot and 608-schema final split are input populations, not
guaranteed eligible reference counts. Rebuild the candidate sets, apply the
policy, run current PostgreSQL DDL and generated-check gates, and publish the
actual surviving counts and exclusion reasons. Do not modify original SQL or
retroactively treat earlier v3 pilot scores as v4 results. The two experimental
arms remain Structured and Direct; repair remains out of scope.
