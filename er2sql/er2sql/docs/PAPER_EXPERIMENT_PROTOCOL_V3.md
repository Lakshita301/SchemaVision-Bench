# ER2SQL paper protocol v3 amendment

This is a prospective amendment for new runs, following the exploratory Qwen and Mistral pilots. It preserves all earlier manifests, source hashes, and reports as historical records. New paid runs must use a newly resolved manifest and the SHA-256 of `config/paper_protocol_v3.yaml`.

## Locked changes

1. **One shared Module 3 prompt.** Module 3 receives only the canonical IR. Its shared prompt requires PostgreSQL syntax, explicit MySQL-to-PostgreSQL type conversion, quoted reserved identifiers, tables before deferred foreign keys, and FK targets that are PRIMARY KEY or UNIQUE. There are no model-specific prompt variants.
2. **No chunking or regeneration.** All candidate profiles request the same 16,384 completion-token cap. If a provider/account/model tier cannot sustain that cap, record the limitation. A `length`/`max_tokens` finish reason alone does not establish an unusable artifact: exclude a paired `(schema_id, tier)` cell from both arms only when the capped output is demonstrably unusable (Module 2 JSON/IR parse or validation failure, or SQL output missing or rejected for syntax at end-of-input). A capped but parseable/validated output remains scored; omitted schema content counts as a model error. Keep other tiers for the same schema. Record the schema, tier, arm/stage, provider finish reason, and evidence of unusability in `evaluation_exclusions.json`. This does not authorize discretionary quality-based exclusions.
3. **Planned-denominator behavioral metrics.** The planned test suite is derived exclusively from Module 1 ground-truth SQL, never from a model's predicted IR or generated SQL. It is the same reference suite for Structured and Direct and across models for each `(schema_id, tier)`; both verification and evaluation use this gold-derived suite. The runner deterministically regenerates the gold suite per artifact, while the evaluator records the gold-SQL SHA-256 and planned test counts per cell; paired comparisons stop with an error if either reference hash or denominator differs between arms. Reviewer-ready definition: **“For each schema-tier cell, planned behavioral tests are derived solely and deterministically from the Module 1 ground-truth SQL; both arms and every model are evaluated against that same gold reference, and no model output determines which tests are planned.”** The primary constraint endpoint is passed planned gold constraint tests divided by all planned gold constraint tests. Missing generation, parse, or compilation contributes zero passes. `macro_cer_all` averages each eligible schema-tier's planned-denominator CER, also assigning zero for pipeline failures. Planned-denominator all-test pass, valid-operation acceptance, and invalid-operation rejection rates are also reported; execution-conditional versions are secondary diagnostics.
4. **One cumulative development set.** `config/development_schemas.json` records the Mistral 10-schema pilot and Groq/Qwen eight-schema pilot. The latter eight were already in the v2 development set; the new registry makes their provenance explicit. The new v3 split carries forward the earlier development list, adds these pilot exposures, and selects a fresh pilot/final set.
5. **Two arms only.** Structured and Direct are evaluated. Repair is out of scope; budget and call projections must not count a repair arm.

## Interpretation and limits

The pilot writeups are recalculated using the new planned-denominator definitions from saved artifacts only; no provider calls are part of recalculation. Historical pilot data remain exploratory and cannot serve as confirmatory evidence. Truncation exclusions reduce the paired scored set and must be disclosed by model and arm; they are not silently counted as model failures or silently dropped from the report. Report assigned and scored schema-tier cells, excluded paired cells/reasons, and full-population compile/generation rates alongside behavioral metrics.

The 16,384-token cap is a common requested cap, not a claim that every provider tier can deliver it. Provider rejection, effective caps, or truncation is a reportable compatibility outcome. Do not lower a single model's cap to improve comparability. Before a v3 paid pilot can pass its local gate, refresh the PostgreSQL evaluator mutation evidence and audit the exact v3 pilot references; the existing v2 evidence is stale for the changed evaluator/source and split.

Budget planning counts two arms: Structured invokes up to Modules 2 and 3; Direct invokes Module 6. For N schema IDs across three tiers, the nominal maximum is 6N artifacts and 9N model calls, excluding bounded transport retries; there are no repair calls. Actual spend projections must be model-specific and recalculated from the exact selected split and each provider's measured pilot token usage/pricing.
